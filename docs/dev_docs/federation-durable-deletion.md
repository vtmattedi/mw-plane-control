# Durable whole-identity deletion

## State and receiver contract

The candidate list is a transactionally captured union of historical consent and assignment applications. It is not an account registry. Internal infrastructure has no local profile and is `exempt`; an ordinary app without a callback is `unresolved` and blocks final deletion.

A deletion operation is `pending`, `legacy_review_required`, or `completed`. Each application delivery is `pending`, `delivering` under a renewable-by-reclaim lease, `confirmed_cleanup`, `no_current_mapping`, `exempt`, `failed` after the retry horizon, or `unresolved`. Only confirmed cleanup, no-current-mapping and explicit infrastructure exemption satisfy an obligation. A transport failure or queued response never confirms erasure.

One transaction disables the identity, records the original request time, revokes central sessions/codes/tokens, creates/reuses the operation and snapshots deliveries. It performs no outbound HTTP. Every delivery has one stable random event ID; retries refresh the short-lived JWT signature under the active signing key without changing operation/event identity or original request time. Outbox/status records have no cascading foreign key to the user. The same disabled subject cannot authenticate or complete new enrollment. Receivers remain responsible for current mapping, idempotent cleanup and fencing app-local handoffs.

The callback payload retains `identity.user.deleted` and signed `reason=account_deleted`, adding `operation_id`. JWT binds issuer, subject, exact client audience, jti/header/body event ID, event, reason, application ID, operation ID and original request time. Receivers must validate the signed operation/event/application/request-time bindings. Consumers must validate all destructive bindings and ignore legacy disconnect events non-destructively.

A receiver must return HTTP 200 with a strict `{"version":1,"outcome":"confirmed_cleanup"}` or `{"version":1,"outcome":"no_current_mapping"}` envelope after its required cleanup and completion receipt commit. Both fields are required; no additional or duplicate fields are accepted. No-current-mapping acknowledges absence of a current mapping, not historical erasure. Empty 200, HTTP 204, unversioned JSON, unsupported versions, malformed/trailing JSON and nonterminal outcomes are never terminal. HTTP 202 remains pending regardless of its body. There is one response parser and no legacy acknowledgement semantics. Asynchronous receivers return 202 until they can confirm a terminal outcome.

Work claims use random lease tokens and atomic SQLite updates. Expired leases can be reclaimed after a crash; stale workers cannot record a result after their lease is replaced. Delivery uses bounded concurrency, a per-request timeout, bounded response body, no redirects and exponential backoff with jitter, capped at one hour, over a seven-day retry horizon. Exhausted work remains `failed` for operator recovery; it is never silently completed. A changed callback/client registration is `unresolved` until an operator reviews and refreshes the snapshot. Disabled/archived apps retain deletion obligations. Finalization requires exactly one existing, disabled subject with a deletion marker and verifies that exactly one row was deleted in the completion transaction. Missing/inconsistent restored subjects and ignored deletes leave the operation pending for operator recovery.

Production callback dialing resolves and checks addresses at connection time, rejecting private, loopback, link-local, unspecified and non-global destinations, and disables environment proxies. This protects against DNS rebinding; HTTPS host validation still uses the registered hostname. Local callback exceptions are available only outside production. Callback response bodies, tokens and raw URLs are not logged.

## Progress and recovery

Initiation returns promptly with a status capability stored in an HttpOnly, SameSite=Strict cookie scoped to `/account/deletion`. Only its hash and 24-hour expiry are stored; neither capability nor identity is put into a URL. Repeated requests, administrative user-delete requests and delivery retries preserve that credential and its original expiry; they do not silently rotate or renew it. The service returns a new token only when the store actually issued it. The browser can revisit `/account/deletion` after normal sign-in sessions are revoked. Status responses are no-store and no-referrer. Operation IDs alone never authorize public access. Closing/reopening the browser retains the status cookie until expiry. Operators use separately authorized status/retry routes after that expiry or browser loss.

Legacy already-disabled identities are imported as `legacy_review_required`, with no fabricated old event IDs and no automated delivery. Operators must reconcile receiver state and original timestamps before explicitly adopting work into the new protocol. This release does not bulk-replay legacy callbacks or WOI `awaiting_contract` receipts.

Durable deletion is always authoritative. Dispatch defaults to true in code and development. Production Compose requires an explicit `IDENTITY_DELETION_DISPATCH_ENABLED=true` or `false` value; `.env.example` sets true. `IDENTITY_DELETION_DISPATCH_ENABLED=false` is a startup dispatch pause: initiation still freezes/revokes, records the operation/outbox and issues progress access. It never selects another implementation. Resume dispatch after receiver contract, backup/recovery and live registration checks; these are deployment prerequisites, not provider compatibility requirements. Existing pending operations, original event IDs, timestamps, capabilities and audited recovery remain intact. There are no new request-bound or `legacy_pending`/`legacy_completed` results. The retained `legacy_review_required` state and operator reconciliation route exist solely to recover already-persisted incomplete deletion requests whose old event IDs cannot be reconstructed.

Emergency pause: set `IDENTITY_DELETION_DISPATCH_ENABLED=false` and recreate/redeploy Identity so the process starts with the updated environment. Resume by setting true and recreating/redeploying again. A plain `docker compose restart` does not reload changed environment values. The switch is startup-only; there is no live pause/resume endpoint or per-application feature flag. Consumers must implement the frozen contract before connection. Already issued callbacks may finish while the old process shuts down; pausing does not undo completed cleanup.

## Retention, backup and rollback

Pending, failed and unresolved work is retained until resolved. Completed records keep minimal subject/event/outcome metadata for 30 days to support status and replay correlation; capabilities expire after 24 hours. Operator retry and snapshot changes are audited. Maintenance must never purge outstanding work. Receivers retain their own idempotency/deletion barriers under their policies; no central tombstone substitutes for those barriers.

Online SQLite backup includes the outbox. Restore only in isolation first; replay receiver completion receipts newer than the backup before exposing traffic, keeping event IDs unchanged. A retry after lost acknowledgement is expected and must be idempotent. Retain original encryption keyrings and signing-key overlap.

Rollback disables worker dispatch first, preserves schema/outbox and leaves deleting identities disabled. Do not run a legacy binary that can reopen or synchronously finalize an outstanding durable deletion. Restore/reconciliation must preserve these records and never claim erasure from a skipped callback. Browser/hardware and production recovery remain separate release gates.

## Operator routes

Use existing Identity administration authorization (`identity.admin`, users read/write permissions) through `/api/identity/` on the BFF or the private Identity `/admin/api/` routes. Mutations require fresh WebAuthn and the BFF requires its existing browser CSRF proof.

- `GET /admin/api/deletions` lists up to 500 recent operations, including migrated legacy requests; only this operator view exposes the subject for reconciliation.
- `GET /admin/api/deletions/{id}` shows per-app outcomes.
- `POST /admin/api/deletion-deliveries/{event}/retry` with `{"refresh_snapshot":false}` reopens failed work; set true only after reviewing a changed registered callback. It resets the retry window without changing the event ID or original requested time.
- `POST /admin/api/deletions/{id}/reconcile-legacy` accepts `outcomes` keyed by client ID and an `evidence_reference`. Every ordinary historical candidate needs verified `confirmed_cleanup` or `no_current_mapping`; infrastructure is exempt. This records terminal operator receipts and finalizes only after all required outcomes, without emitting invented historical callbacks. An unavailable app cannot be marked complete without evidence.
- Private `GET /metrics/deletions` exposes aggregate queue age/outstanding/failure counts plus `dispatch_enabled` (0/1), `pending_operations` (all unfinished operations, including operator-review and finalization-only work), and `dispatch_paused_with_pending` (1 when dispatch is disabled and unfinished operations exist). Alert on `dispatch_paused_with_pending=1`. Values are recomputed on each scrape, including deletions initiated after a paused startup; the gateway blocks the metrics prefix. No subject, client or token labels are included.

Reconciliation is an operator attestation, not automated proof of application erasure. Retain the referenced support evidence in approved storage. No bulk replay is provided.
